2. Логи собирает внешний шиппер (Fluent Bit по умолчанию) и передаёт по OTLP; eBPF-агент логи не читает.

4. Детектор метрик — робастная статистика (медиана/MAD) с сезонным профилем; EWMA остаётся сглаженной базовой линией.

Также принято: разбор HTTP/2 + HPACK входит в MVP (иначе gRPC не наблюдаем на уровне методов), обязательный HA-профиль развёртывания + single-node профиль для разработки.

## 1. Видение и границы системы

### 1.1. Проблема

В кластере Kubernetes с десятками микросервисов дежурный инженер при инциденте тратит основное время не на исправление, а на поиск: какой сервис сломался первым, а какие пострадали каскадом. Типичные препятствия:

- **Карта зависимостей устаревает.** Документированная архитектура расходится с реальными вызовами; новые зависимости появляются с каждым релизом.
- **Не все сервисы инструментированы.** Внедрение OpenTelemetry SDK требует изменений кода и релизов; легаси и сторонние сервисы остаются «тёмными пятнами».
- **Метрики и логи анализируются раздельно.** Всплеск латентности виден на дашборде, новая ошибка — в логах, но связать их приходится вручную.
- **Статические пороги шумят.** Пороговые алерты либо срабатывают на суточные колебания трафика, либо пропускают реальные деградации.

### 1.2. Цель

Создать open source систему, которая без изменения кода сервисов строит живой граф зависимостей микросервисов, обнаруживает аномалии в метриках и логах и за время не более 2 минут указывает дежурному ранжированный список вероятных первопричин с доказательствами.

### 1.3. Границы: входит в скоуп

- Платформа: Linux, Kubernetes, один кластер на установку.
- Источники данных: собственный eBPF-агент (HTTP/1.1, HTTP/2, gRPC без TLS на уровне приложения), приём OTLP (traces, metrics, logs), логи через внешний OTLP-шиппер.
- Обработка: потоковая агрегация в окнах событийного времени, построение графа зависимостей, детекция аномалий метрик и логов, корреляция в инциденты, ранжирование первопричин (RCA), алертинг.
- Интерфейсы: API (gRPC / gRPC-Web / Connect-JSON), веб-интерфейс, CLI.
- Эксплуатация: Helm-чарт с профилями `dev` и `ha`, самонаблюдаемость, мультитенантность на уровне namespace, RBAC, OIDC.

### 1.4. Границы: явно не входит в скоуп

| Не входит | Причина / куда вынесено |
|---|---|
| Расшифровка TLS (uprobes на OpenSSL/Go crypto/tls) | Раздел 11, «Развитие» |
| Протоколы БД (PostgreSQL, MySQL, Redis), Kafka-протокол | Раздел 11 |
| Мультикластер, федерация | Раздел 11 |
| Windows, macOS как наблюдаемые узлы; bare-metal без Kubernetes | Раздел 11 |
| Хранение и показ полного распределённого трейса (APM-водопад) | Система использует спаны как источник рёбер и метрик, а не как трейсинг-бэкенд; полноценный просмотр трейсов — раздел 11 |
| Автоматическое исправление (auto-remediation) | Раздел 11 |

| Сбор логов с узлов собственным агентом | Принятое решение: логи доставляет внешний шиппер по OTLP |

## 2. Заинтересованные стороны и персоны

| Персона | Цели | Боли |
|---|---|---|
| **SRE** — отвечает за надёжность платформы, строит SLO | Видеть реальную топологию и «горячие» рёбра; находить системные деградации до пользователей; сократить MTTR | Карта сервисов устаревает; дашборды не связаны с логами; шум алертов съедает доверие |
| **Разработчик сервиса** — владеет 1–3 сервисами | Понять, как его релиз повлиял на соседей; увидеть новые ошибки в логах своего сервиса | Нет времени внедрять OTel SDK; логи большие, новые ошибки тонут в потоке |
| **Дежурный инженер (on-call)** — реагирует на инциденты ночью | Из алерта за минуты попасть к первопричине; не будиться из-за шума | Алерт «вырос error rate у gateway» — а сломалась БД через три хопа; 20 алертов на один инцидент |
| **Администратор платформы** — устанавливает и обслуживает систему | Установить за минуты, обновлять без потерь; контролировать ресурсы и доступ команд | Агенты мониторинга сами нагружают узлы; привилегированные DaemonSet'ы; хрупкие апгрейды |
| **Научный руководитель / комиссия** (вторичная) | Увидеть новизну, измеримые результаты и воспроизводимые эксперименты | Работы без количественной оценки |

## 3. Пользовательские сценарии

**UC-01. Дежурный находит первопричину за 2 минуты.**
В 03:12 дежурный получает уведомление «Инцидент #142: деградация checkout, 4 сервиса». В уведомлении есть ссылка на инцидент. На странице инцидента подграф из 4 сервисов: `checkout` и `cart` подсвечены как пострадавшие, `payment-db-proxy` — как кандидат №1 с оценкой 0.82. Доказательства: p95 латентности вырос с 40 до 900 мс, появился новый шаблон лога `connection pool exhausted (<*> waiters)`. Дежурный переходит к логам по шаблону и подтверждает гипотезу. Затрачено менее 2 минут, 3 клика от уведомления до кандидата. (FR-ALR-005, FR-RCA-002, FR-RCA-003, FR-UI-005, NFR-USAB-002)

**UC-02. SRE видит топологию нового кластера без изменения кода.**
SRE ставит Helm-чарт в профиле `dev` и запускает тестовое приложение из 11 сервисов, ни один из которых не инструментирован. Через 10 минут после `helm install` в UI отображён граф со всеми фактическими рёбрами, включая gRPC-методы и внешний платёжный API как внешний узел. (FR-AGT-001…003, FR-TOP-001, FR-TOP-003, FR-UI-001, NFR-USAB-001)

**UC-03. Разработчик оценивает свой релиз.**
Разработчик выкатывает новую версию `recommendation`. Через 2 минуты система создаёт инцидент: error rate ребра `frontend → recommendation` вырос до 12%, у `recommendation` появился новый шаблон лога уровня ERROR. Событие деплоя указано среди кандидатов первопричины. (FR-MAD-001, FR-LAD-003, FR-RCA-004)

**UC-04. SRE разбирает ночной инцидент постфактум.**
Утром SRE открывает граф в режиме «машины времени» на 03:00–03:30 и проигрывает изменения рёбер с шагом 10 секунд. Видно, когда появилась задержка на ребре к прокси БД и как она распространилась вверх. (FR-TOP-006, FR-UI-004)

**UC-05. Администратор подключает новую команду.**
Администратор переводит установку на профиль `ha`, подключает корпоративный OIDC-провайдер, создаёт тенант `team-payments` с namespaces `payments-*` и выдаёт группе роль `editor`. Участники команды видят только свои namespaces и рёбра, входящие в них. (FR-OPS-001, FR-SEC-001, FR-SEC-003, FR-SEC-004)

**UC-06. Дежурный глушит алерт на время работ.**
Перед плановой миграцией БД дежурный создаёт silence на 2 часа по матчеру `service=orders-db` прямо со страницы алерта. Уведомления по этому сервису не отправляются, но аномалии и инциденты продолжают записываться. (FR-ALR-004, FR-UI-007)

**UC-07. Инструментированные и неинструментированные сервисы на одном графе.**
Сервис `orders` отправляет OTLP-трейсы через SDK, сервис `inventory` не инструментирован. Ребро `orders → inventory` отображается один раз, а не дважды. Его метрики берутся из источника с более высоким приоритетом, источник указан в панели ребра. (FR-TOP-004, FR-ING-001)

**UC-08. Узел бэкенда падает, данные не теряются.**
В профиле `ha` узел с одной из реплик NATS и процессором выключают. Клиенты OTLP получают кратковременные retryable-ответы и повторяют отправку. Подтверждённые до сбоя события не теряются, граф продолжает обновляться через 60 секунд. Администратор получает self-alert «processor replica lost». (NFR-REL-001, NFR-REL-003, NFR-SELF-003)

## 4. Функциональные требования

Формат: **Требование** — формулировка «Система должна…»; **Обоснование** — зачем и для какой персоны; **Приёмка** — Given / When / Then; **Приоритет** — MoSCoW; **Зависит от** — другие требования.

### 4.1. eBPF-агент (AGT)

#### FR-AGT-001 — Наблюдение HTTP/1.1
- **Требование:** Система должна для каждого HTTP/1.1-обмена между процессами в подах узла фиксировать: направление (client/server), метод, путь без query-строки, статус ответа, время начала, длительность (от первого байта запроса до последнего байта ответа), размер запроса и ответа, адреса обеих сторон.
- **Обоснование:** Рёбра графа и RED-метрики для неинструментированных сервисов (SRE, разработчик).
- **Приёмка:** Given под с сервером на Go `net/http` и клиентом, выполняющим 1000 запросов `GET /items/42` со статусом 200 и 100 запросов со статусом 503; When агент работает на узле; Then в хранилище есть 1100 записей с корректными методом, путём, статусом, а медиана зафиксированной длительности отличается от измеренной клиентом не более чем на 1 мс.
- **Приоритет:** Must · **Зависит от:** FR-AGT-004, FR-AGT-005

#### FR-AGT-002 — Наблюдение HTTP/2 и gRPC с HPACK
- **Требование:** Система должна разбирать кадры HTTP/2, вести состояние HPACK-декодера для каждого соединения в каждом направлении и для каждого потока (stream) фиксировать: `:method`, `:path` (для gRPC — сервис и метод), `:status`, `grpc-status` из трейлеров, время начала, длительность и размеры.
- **Обоснование:** gRPC — основной протокол межсервисного взаимодействия; без HPACK метод и статус недоступны (SRE, дежурный).
- **Приёмка:** Given приложение Online Boutique (gRPC, Go/Java/Python/Node/C#) запущено после старта агента; When сгенерировано 10 000 gRPC-вызовов; Then ≥ 99% вызовов записаны с корректными методом и `grpc-status` при сверке с эталонными OTel-спанами (см. NFR-COMPAT-002).
- **Приоритет:** Must · **Зависит от:** FR-AGT-001, FR-AGT-003

#### FR-AGT-003 — Деградация до уровня L4
- **Требование:** Система должна для TCP-соединений, протокол которых не распознан или состояние HPACK которых неполно (соединение открыто до старта агента), фиксировать на уровне L4: стороны соединения, число переданных байт в каждую сторону, время установления соединения и признак «протокол неизвестен / заголовки недоступны».
- **Обоснование:** Ребро графа не должно пропадать из-за того, что метод не разобран; дежурный видит хотя бы факт зависимости.
- **Приёмка:** Given gRPC-соединение установлено до запуска агента, а клиент использует индексированные заголовки из динамической таблицы; When агент запущен и идёт трафик; Then в графе есть ребро между сервисами с ненулевым объёмом байт и пометкой `l7=unavailable`, а записей с неверно декодированным методом нет.
- **Приоритет:** Must · **Зависит от:** FR-AGT-004

#### FR-AGT-004 — Ограничение наблюдения подами своего узла
- **Требование:** Система должна учитывать только сокеты процессов, принадлежащих контейнерам подов узла, на котором работает экземпляр агента (определение по cgroup), и игнорировать трафик процессов хоста и чужих узлов.
- **Обоснование:** Без этого на узлах с общим ядром (kind, вложенная виртуализация) события дублируются, а трафик системных процессов засоряет граф (администратор, SRE).
- **Приёмка:** Given кластер kind из 2 рабочих узлов на одном ядре, на каждом по агенту, и один HTTP-вызов между подами разных узлов; When вызов выполнен; Then в хранилище ровно 2 записи (client-сторона от агента узла A и server-сторона от агента узла B), а не 4.
- **Приоритет:** Must · **Зависит от:** —

#### FR-AGT-005 — Привязка событий к метаданным Kubernetes
- **Требование:** Система должна каждому событию агента сопоставлять для локальной стороны: namespace, имя и UID пода, имя контейнера, владельца верхнего уровня (Deployment/StatefulSet/DaemonSet/Job), метки `app.kubernetes.io/name` и `app.kubernetes.io/version`.
- **Обоснование:** Граф строится на уровне сервисов и workload'ов, а не PID и IP (все персоны).
- **Приёмка:** Given под Deployment `cart` с ReplicaSet `cart-7d9f`; When под отвечает на запрос; Then событие содержит `workload=Deployment/cart`, а не `ReplicaSet/cart-7d9f`; события пода, созданного менее 5 с назад, обогащены не менее чем в 99% случаев.
- **Приоритет:** Must · **Зависит от:** FR-AGT-004

#### FR-AGT-006 — Учёт потерь событий
- **Требование:** Система должна считать каждое событие, потерянное агентом (переполнение кольцевого буфера ядра, превышение лимита памяти, отказ отправки), по причине потери и экспортировать эти счётчики; ни одна потеря не должна быть неучтённой.
- **Обоснование:** Администратор и SRE должны знать, что граф неполон, а не получать молча искажённую картину.
- **Приёмка:** Given кольцевой буфер уменьшен до 64 КиБ и подан трафик 20 000 запросов/с; When буфер переполняется; Then сумма «доставлено + учтено как потерянное» равна числу запросов, зафиксированному генератором нагрузки, с погрешностью 0.
- **Приоритет:** Must · **Зависит от:** FR-OPS-004

#### FR-AGT-007 — Защита бюджета ресурсов узла
- **Требование:** Система должна при превышении агентом заданного бюджета CPU (по умолчанию 2% ёмкости узла, усреднение за 10 с) переходить на детерминированную выборку событий с коэффициентом, достаточным для возврата в бюджет, и отмечать в событиях коэффициент выборки для корректного пересчёта RED-метрик.
- **Обоснование:** Агент мониторинга не должен становиться причиной инцидента (администратор).
- **Приёмка:** Given нагрузка на узел в 4 раза выше номинальной (NFR-AGT-001); When агент работает 10 мин; Then CPU агента ≤ 2.5% ёмкости узла на любом 1-минутном интервале, а расчётный rate по выборке отличается от фактического не более чем на 5%.
- **Приоритет:** Should · **Зависит от:** FR-AGT-006

#### FR-AGT-008 — Буферизация при недоступности приёма
- **Требование:** Система должна при недоступности приёмника буферизовать события агента в памяти в пределах ограничения (по умолчанию 64 МиБ) и отправить их после восстановления связи; при исчерпании буфера — отбрасывать самые старые события с учётом по FR-AGT-006.
- **Обоснование:** Кратковременный рестарт бэкенда не должен создавать дыры в графе (SRE).
- **Приёмка:** Given приёмник недоступен 30 с при нагрузке 2000 событий/с; When связь восстановлена; Then все 60 000 событий доставлены, потерь 0, а RSS агента за время сбоя не превысил лимит NFR-AGT-003.
- **Приоритет:** Must · **Зависит от:** FR-AGT-006, FR-ING-002

#### FR-AGT-009 — Минимизация захватываемых данных
- **Требование:** Система должна передавать за пределы узла только поля из FR-AGT-001…003 и заголовки из явного allowlist (по умолчанию: `:authority`, `host`, `content-type`, `user-agent`, `traceparent`); тела запросов и ответов, а также заголовки `authorization`, `cookie`, `set-cookie` не должны покидать узел ни при какой конфигурации.
- **Обоснование:** PII и секреты в телах и заголовках (администратор, безопасность).
- **Приёмка:** Given запросы с телом, содержащим e-mail, и заголовком `Authorization: Bearer <JWT>`; When трафик наблюдается 5 мин; Then в сетевом потоке агент → приёмник и в хранилище не найдено ни одного вхождения e-mail и JWT (поиск по подстроке).
- **Приоритет:** Must · **Зависит от:** FR-AGT-001, FR-AGT-002

#### FR-AGT-010 — Проверка совместимости при старте
- **Требование:** Система должна при старте агента проверять версию ядра, наличие BTF и необходимых возможностей eBPF (раздел 6) и при несоответствии завершаться с кодом ошибки и сообщением, называющим недостающую возможность, а не работать частично без индикации.
- **Обоснование:** Администратор должен за минуту понять, почему агент не работает на конкретном узле.
- **Приёмка:** Given узел без `/sys/kernel/btf/vmlinux`; When запускается агент; Then под переходит в `CrashLoopBackOff`, в логе есть сообщение `kernel BTF not available` с ссылкой на документацию, а `faultctl doctor` (FR-CLI-003) показывает этот узел как неподдерживаемый.
- **Приоритет:** Must · **Зависит от:** —

### 4.2. Приём данных (ING)

#### FR-ING-001 — Приём OTLP
- **Требование:** Система должна принимать трейсы, метрики и логи по OTLP v1 через gRPC и HTTP/protobuf и преобразовывать их во внутреннюю модель событий с идентификацией сервиса по атрибутам ресурса `service.name`, `service.namespace`, `k8s.namespace.name`, `k8s.pod.name`.
- **Обоснование:** Совместимость с экосистемой OpenTelemetry и логами через шиппер (разработчик, SRE).
- **Приёмка:** Given `telemetrygen` отправляет 10 000 спанов, 10 000 записей логов и 10 000 точек метрик по gRPC и столько же по HTTP; When приём завершён; Then все 60 000 элементов доступны через API с корректной привязкой к сервису.
- **Приоритет:** Must · **Зависит от:** FR-ING-003

#### FR-ING-002 — Приём событий агента
- **Требование:** Система должна принимать пакеты событий от агентов с подтверждением каждого пакета, аутентифицируя агента по FR-SEC-002.
- **Обоснование:** Канал доставки данных eBPF-агента (SRE).
- **Приёмка:** Given агент отправляет пакет из 500 событий; When пакет успешно сохранён; Then агент получает подтверждение с идентификатором пакета, а пакет без валидного токена отклоняется с кодом `UNAUTHENTICATED`.
- **Приоритет:** Must · **Зависит от:** FR-ING-003, FR-SEC-002

#### FR-ING-003 — Подтверждение только после надёжной записи
- **Требование:** Система должна отвечать отправителю об успехе (OTLP-ответ без ошибки / подтверждение пакета) только после того, как пакет сохранён в транспортном журнале с заданным фактором репликации (профиль `ha` — подтверждение кворумом из 3 реплик).
- **Обоснование:** Определяет понятие «подтверждённое событие» для NFR-REL-001 (администратор).
- **Приёмка:** Given профиль `ha`, и две из трёх реплик журнала недоступны; When клиент отправляет пакет; Then клиент получает retryable-ошибку (`UNAVAILABLE` / HTTP 503), а не успех.
- **Приоритет:** Must · **Зависит от:** —

#### FR-ING-004 — Дедупликация повторно отправленных пакетов
- **Требование:** Система должна распознавать повторную отправку пакета агента с тем же идентификатором в течение окна дедупликации (по умолчанию 2 мин) и не создавать дубликатов событий.
- **Обоснование:** Ретраи после таймаута при неизвестном исходе не должны удваивать rate на графе (SRE).
- **Приёмка:** Given пакет из 500 событий успешно сохранён, но подтверждение потеряно; When агент повторно отправляет тот же пакет через 10 с; Then в хранилище 500 событий, а не 1000, и агент получает успешное подтверждение.
- **Приоритет:** Must · **Зависит от:** FR-ING-002

#### FR-ING-005 — Обратное давление при перегрузке
- **Требование:** Система должна при превышении пропускной способности или лимита тенанта отвечать retryable-кодом (`RESOURCE_EXHAUSTED` / HTTP 429 с `Retry-After`) без завершения процесса и без потери уже принятых данных.
- **Обоснование:** Стандартная семантика OTLP-ретраев; защита бэкенда от каскадного отказа (администратор).
- **Приёмка:** Given входной поток в 2 раза выше NFR-PERF-001; When нагрузка длится 5 мин; Then процесс приёма не перезапускался (restartCount не изменился), часть запросов получила 429/`RESOURCE_EXHAUSTED`, и все запросы, получившие успех, присутствуют в хранилище.
- **Приоритет:** Must · **Зависит от:** FR-ING-003

#### FR-ING-006 — Валидация и лимиты входных данных
- **Требование:** Система должна отклонять запросы больше 4 МиБ, усекать значения атрибутов до 4 КиБ и тела логов до 16 КиБ, отбрасывать атрибуты сверх 128 на элемент и сообщать о частично отклонённых элементах через OTLP `partial_success` с указанием количества.
- **Обоснование:** Защита от некорректных клиентов и раздувания хранилища (администратор).
- **Приёмка:** Given запрос из 100 логов, 3 из которых имеют тело 64 КиБ, а 2 — 200 атрибутов; When запрос принят; Then сохранено 100 логов, 3 тела усечены до 16 КиБ с атрибутом `faultline.truncated=true`, а ответ содержит `partial_success` с ненулевым счётчиком и сообщением.
- **Приоритет:** Should · **Зависит от:** FR-ING-001

### 4.3. Движок потоковой обработки (STR)

#### FR-STR-001 — Окна событийного времени с ранними результатами
- **Требование:** Система должна агрегировать события в неперекрывающихся (tumbling) окнах событийного времени заданного размера (по умолчанию 10 с) по ключу и выдавать предварительный результат окна с периодом не более 1 с по времени обработки и финальный результат при прохождении watermark через конец окна.
- **Обоснование:** Ранние результаты нужны для NFR-PERF-003 (свежесть графа < 5 с), финальные — для точных метрик и детекторов (SRE, дежурный).
- **Приёмка:** Given поток 1000 событий/с с равномерным событийным временем; When наступает конец окна; Then подписчик получает не менее 9 предварительных результатов окна до финального, а финальный результат совпадает с пакетным пересчётом по сырым событиям в ClickHouse.
- **Приоритет:** Must · **Зависит от:** FR-STR-002

#### FR-STR-002 — Границы допустимого событийного времени
- **Требование:** Система должна вычислять watermark как минимум по партициям из `max(event_time) − allowed_lateness` (по умолчанию 30 с); события, опоздавшие не более allowed lateness, учитывать с выпуском обновлённого результата окна; события, опоздавшие сильнее, сохранять в сыром виде, исключать из агрегатов и учитывать в счётчике `late_dropped`; события со временем более чем на 5 мин в будущем относительно времени приёма — переназначать на время приёма с пометкой `clock_skew=true`.
- **Обоснование:** Расхождение часов узлов и задержки доставки не должны искажать метрики или блокировать окна (SRE).
- **Приёмка:** Given окно [12:00:00, 12:00:10) закрыто финально; When приходят событие с временем 12:00:05 при watermark 12:00:30 (опоздание 25 с) и событие с временем 12:00:05 при watermark 12:00:50; Then первое приводит к выпуску обновлённого окна, второе увеличивает `late_dropped` на 1 и присутствует в сырых данных; событие со временем «сейчас + 1 час» записано со временем приёма и пометкой.
- **Приоритет:** Must · **Зависит от:** —

#### FR-STR-003 — Чекпоинты и восстановление состояния
- **Требование:** Система должна не реже чем раз в 10 с сохранять согласованный снимок состояния обработчика (открытые окна, состояние детекторов, дерево шаблонов логов, позиции чтения из журнала) и после перезапуска восстанавливать состояние из последнего снимка с повторной обработкой журнала с сохранённой позиции.
- **Обоснование:** Перезапуск процессора (деплой, OOM, отказ узла) не должен сбрасывать обученные детекторы и терять открытые окна (SRE, администратор).
- **Приёмка:** Given процессор обработал 30 мин трафика, детекторы в состоянии `active`; When под процессора убит `SIGKILL`; Then после рестарта детекторы в состоянии `active` (не `learning`), а агрегаты окон за период сбоя совпадают с пакетным пересчётом (NFR-REL-002).
- **Приоритет:** Must · **Зависит от:** FR-STR-004

#### FR-STR-004 — Идемпотентный вывод результатов
- **Требование:** Система должна присваивать каждому результату окна детерминированный идентификатор (ключ, начало окна, версия) так, чтобы повторная запись результата после восстановления не приводила к двойному учёту в хранилище и у подписчиков.
- **Обоснование:** Повторная обработка журнала после FR-STR-003 неизбежна; двойной счёт исказит rate и вызовет ложные аномалии.
- **Приёмка:** Given результаты окон за 5 мин записаны; When тот же отрезок журнала обработан повторно; Then запрос `sum(requests)` за этот интервал возвращает то же значение, что до повтора.
- **Приоритет:** Must · **Зависит от:** —

#### FR-STR-005 — Горизонтальное масштабирование по ключу
- **Требование:** Система должна распределять ключи обработки (тенант + сервис) между N экземплярами процессора так, что каждый ключ обрабатывается ровно одним экземпляром, и перераспределять ключи при добавлении или потере экземпляра не дольше чем за 60 с.
- **Обоснование:** Масштабирование под рост кластера и переживание отказа экземпляра (администратор).
- **Приёмка:** Given 2 экземпляра процессора; When добавлен третий, а через 10 мин один из трёх удалён; Then в каждый момент нет ключа, обрабатываемого двумя экземплярами (проверка по журналу владения), и через 60 с после каждого изменения все ключи имеют владельца.
- **Приоритет:** Should · **Зависит от:** FR-STR-003

#### FR-STR-006 — Нормализация путей URL
- **Требование:** Система должна приводить пути HTTP к шаблонам маршрутов, заменяя сегменты-идентификаторы (десятичные числа, UUID, hex длиной ≥ 16, base64-подобные токены длиной ≥ 20) на плейсхолдер `{id}`, и применять пользовательские правила-переопределения для сервиса.
- **Обоснование:** `/users/1`, `/users/2`, … взрывают кардинальность и делают RED-метрики бесполезными (SRE).
- **Приёмка:** Given 10 000 запросов к `/users/<случайный id>/orders/<uuid>`; When они агрегированы; Then образуется одна серия `/users/{id}/orders/{id}`.
- **Приоритет:** Must · **Зависит от:** FR-AGT-001

#### FR-STR-007 — Ограничение кардинальности
- **Требование:** Система должна ограничивать число активных серий на тенант (по умолчанию 100 000) и уникальных шаблонов путей на сервис (по умолчанию 500); при превышении — агрегировать новые значения в серию `__overflow__`, увеличивать счётчик переполнения и генерировать self-alert.
- **Обоснование:** Взрыв кардинальности — частая причина падения систем мониторинга (администратор).
- **Приёмка:** Given лимит путей сервиса 500; When сервис получает запросы к 2000 уникальным нормализованным путям; Then у сервиса ровно 501 серия (500 + `__overflow__`), память процессора не растёт сверх NFR-PERF-002, и сработал self-alert `cardinality_limit_reached`.
- **Приоритет:** Must · **Зависит от:** FR-STR-006, NFR-SELF-003

### 4.4. Граф зависимостей (TOP)

#### FR-TOP-001 — Построение рёбер на нескольких уровнях
- **Требование:** Система должна строить направленный граф «вызывающий → вызываемый» на уровнях workload, namespace и pod из событий агента и пар client/server-спанов OTLP, выделяя для рёбер L7 протокол и операцию (HTTP-маршрут или gRPC-метод).
- **Обоснование:** Ядро темы №26 — визуализация реальных зависимостей (все персоны).
- **Приёмка:** Given Online Boutique с известной эталонной топологией (14 рёбер на уровне workload); When трафик идёт 5 мин; Then граф на уровне workload содержит все 14 рёбер и ни одного лишнего (NFR-ACC-005), а свёртка до уровня namespace даёт корректные агрегированные рёбра.
- **Приоритет:** Must · **Зависит от:** FR-TOP-003, FR-STR-001

#### FR-TOP-002 — RED-метрики ребра и узла
- **Требование:** Система должна для каждого ребра и узла в каждом окне вычислять: rate (запросов/с), долю ошибок (HTTP 5xx, gRPC-статусы, кроме `OK`, `NOT_FOUND`, `ALREADY_EXISTS`, `CANCELLED`; ошибкой вызова считается ошибка, увиденная любой из сторон — вызывающей или вызываемой), латентность p50/p95/p99 с относительной ошибкой квантиля не более 2%.
- **Обоснование:** Здоровье зависимости — входные сигналы детекторов и цвет рёбер в UI (SRE, дежурный).
- **Приёмка:** Given синтетический поток с известным распределением латентности (логнормальное, 100 000 запросов); When вычислены квантили; Then p50/p95/p99 отличаются от точных не более чем на 2%.
- **Приоритет:** Must · **Зависит от:** FR-STR-001

#### FR-TOP-003 — Разрешение адреса пира с учётом времени
- **Требование:** Система должна сопоставлять удалённый IP:порт с подом/сервисом по интервалам владения адресом `[создание, удаление)`, используя состояние на момент события, а не на момент обработки; ClusterIP сервиса — разрешать в сервис; неразрешённые адреса — относить к внешним узлам, группируя по DNS-имени (если известно) или по /24 подсети.
- **Обоснование:** IP подов переиспользуются через секунды после удаления; без учёта времени события рёбра «прыгают» к чужому сервису (SRE).
- **Приёмка:** Given под A с IP 10.0.1.5 удалён в 12:00:00, а под B получил тот же IP в 12:00:03; When обрабатывается опоздавшее событие со временем 11:59:59 и адресом 10.0.1.5; Then ребро ведёт к A, а не к B.
- **Приоритет:** Must · **Зависит от:** FR-AGT-005

#### FR-TOP-004 — Слияние источников без дублирования
- **Требование:** Система должна, если один и тот же вызов наблюдается несколькими источниками (агент client-side, агент server-side, OTLP-спан), учитывать его в метриках ребра один раз, выбирая источник по настраиваемому приоритету (по умолчанию OTLP-спан > агент server-side > агент client-side), и указывать использованный источник в данных ребра.
- **Обоснование:** Иначе rate удваивается или утраивается при смешанном инструментировании (UC-07).
- **Приёмка:** Given инструментированный сервис `orders` вызывает неинструментированный `inventory` 1000 раз; When агент работает на обоих узлах; Then rate ребра `orders → inventory` соответствует 1000 вызовам (±1%), и источник ребра — `otlp`.
- **Приоритет:** Must · **Зависит от:** FR-TOP-001

#### FR-TOP-005 — Устаревание рёбер
- **Требование:** Система должна помечать ребро как неактивное, если по нему нет трафика 5 мин, и исключать его из живого графа через 24 ч без трафика; история ребра сохраняется по сроку хранения FR-STO-001.
- **Обоснование:** Граф не должен засоряться удалёнными зависимостями (SRE).
- **Приёмка:** Given ребро без трафика; When прошло 5 мин; Then в живом графе оно имеет статус `inactive`; When прошло 24 ч; Then его нет в живом графе, но оно возвращается запросом графа на момент, когда оно было активно.
- **Приоритет:** Should · **Зависит от:** FR-TOP-001

#### FR-TOP-006 — Граф на момент времени
- **Требование:** Система должна возвращать состояние графа (узлы, рёбра, RED-метрики, аномалии) на любой момент в пределах срока хранения с разрешением 10 с для последних 7 суток и 1 мин для более старых данных.
- **Обоснование:** Разбор инцидентов постфактум (UC-04).
- **Приёмка:** Given инцидент 6 ч назад; When запрошен граф на момент инцидента; Then возвращённые рёбра и метрики совпадают с теми, что были показаны в живом графе в тот момент (сверка с журналом стрима).
- **Приоритет:** Should · **Зависит от:** FR-STO-002

### 4.5. Детектор аномалий метрик (MAD)

#### FR-MAD-001 — Робастная детекция по RED-сигналам
- **Требование:** Система должна для каждого узла и ребра детектировать аномалии rate, доли ошибок и p95 латентности по робастной оценке `score = |x − median| / (1.4826 · MAD)` относительно скользящей базовой линии за 1 ч (с учётом сезонного профиля по FR-MAD-002), признавать аномалией превышение порога k (по умолчанию 4) в 3 окнах подряд и выдавать запись аномалии с полями: объект, сигнал, направление, score, наблюдаемое значение, ожидаемый диапазон, время начала.
- **Обоснование:** Обычный z-score «отравляется» самими выбросами; требование 3 окон подряд — первый уровень гистерезиса против шума (дежурный).
- **Приёмка:** Given сервис со стабильным p95 = 50 мс ± 5 мс в течение 1 ч; When через Chaos Mesh вносится задержка +300 мс; Then аномалия p95 с направлением `up` создана не позднее 60 с после внесения сбоя (NFR-ACC-001); When одиночный выброс в 1 окне; Then аномалия не создаётся.
- **Приоритет:** Must · **Зависит от:** FR-TOP-002, FR-MAD-003

#### FR-MAD-002 — Сезонный профиль
- **Требование:** Система должна строить для каждого сигнала профиль ожидаемого значения по часу суток после накопления 3 суток истории и по часу недели после 14 суток и использовать его как базу для FR-MAD-001.
- **Обоснование:** Суточный спад трафика ночью без сезонности даёт ложные аномалии rate (дежурный).
- **Приёмка:** Given 14 суток синтетического трафика с суточной синусоидой (амплитуда ±60%) и без сбоев; When прогнаны 15-е сутки по тому же профилю; Then аномалий rate не создано; Given те же данные без сезонного профиля; Then аномалии создаются (контрольный эксперимент для диплома).
- **Приоритет:** Should · **Зависит от:** FR-STR-003

#### FR-MAD-003 — Холодный старт
- **Требование:** Система должна держать детектор нового сигнала в состоянии `learning` до накопления 60 окон и не создавать по нему аномалий; состояние детектора должно быть доступно через API и UI.
- **Обоснование:** Новые сервисы без истории не должны генерировать шквал алертов (дежурный).
- **Приёмка:** Given новый сервис появился на графе; When прошло 5 мин (30 окон) с хаотичной нагрузкой; Then аномалий по нему нет, а API возвращает `detector_state=learning, progress=50%`.
- **Приоритет:** Must · **Зависит от:** —

#### FR-MAD-004 — Порог значимости для малого трафика
- **Требование:** Система должна не создавать аномалии: rate — при медиане базовой линии ниже 0.2 запросов/с; доли ошибок — если в окне меньше 5 ошибочных запросов; латентности — если в окне меньше 20 запросов.
- **Обоснование:** На малых выборках 1 ошибка из 2 запросов — это 50% error rate и ложный алерт (дежурный).
- **Приёмка:** Given сервис с 1 запросом/10 с; When один запрос вернул 500; Then аномалия error rate не создаётся.
- **Приоритет:** Must · **Зависит от:** FR-MAD-001

### 4.6. Детектор аномалий логов (LAD)

#### FR-LAD-001 — Онлайн-извлечение шаблонов
- **Требование:** Система должна для каждого сервиса в потоке извлекать шаблоны логов алгоритмом семейства Drain (дерево фиксированной глубины, порог сходства по умолчанию 0.4) и присваивать каждой записи лога идентификатор шаблона.
- **Обоснование:** Ядро темы №29 — переход от миллионов строк к сотням шаблонов (разработчик, дежурный).
- **Приёмка:** Given датасет LogHub-2k HDFS; When он пропущен через систему; Then Grouping Accuracy соответствует NFR-ACC-004, а каждая запись имеет `template_id`.
- **Приоритет:** Must · **Зависит от:** FR-LAD-002, FR-ING-001

#### FR-LAD-002 — Маскирование переменных до майнинга
- **Требование:** Система должна до извлечения шаблона заменять в тексте лога токены IPv4/IPv6, UUID, числа, hex-строки длиной ≥ 8, e-mail, URL и пути файлов на типизированные плейсхолдеры (`<IP>`, `<UUID>`, `<NUM>`, …) с поддержкой пользовательских регулярных выражений.
- **Обоснование:** Повышает точность группировки и одновременно не даёт PII попасть в текст шаблона.
- **Приёмка:** Given строки `user 42 logged from 10.1.2.3` и `user 7 logged from 10.1.2.9`; When они обработаны; Then обе имеют один шаблон `user <NUM> logged from <IP>`.
- **Приоритет:** Must · **Зависит от:** —

#### FR-LAD-003 — Детекция нового шаблона
- **Требование:** Система должна создавать аномалию «новый шаблон», если у сервиса с детектором в состоянии `active` (не менее 1 ч наблюдения) появился шаблон, не встречавшийся ранее, с уровнем ERROR или выше; для уровня WARN — если он встретился не менее 5 раз за 1 мин.
- **Обоснование:** Новая ошибка после релиза — сильнейший сигнал первопричины (UC-03).
- **Приёмка:** Given сервис логирует 10 известных шаблонов 2 ч; When появляется `ERROR connection pool exhausted (12 waiters)`; Then аномалия `new_template` создана не позднее 30 с после первой записи и содержит пример строки.
- **Приоритет:** Must · **Зависит от:** FR-LAD-001

#### FR-LAD-004 — Изменение частоты шаблона
- **Требование:** Система должна детектировать всплеск частоты шаблона и исчезновение ранее регулярного шаблона (встречавшегося в ≥ 90% окон по 1 мин за последний 1 ч), используя робастную оценку FR-MAD-001 и пороги значимости FR-MAD-004.
- **Обоснование:** Рост `retrying request` в 50 раз или пропажа heartbeat-лога говорят о деградации раньше метрик (SRE).
- **Приёмка:** Given шаблон heartbeat пишется раз в 10 с более 1 ч; When сервис перестаёт его писать; Then аномалия `template_disappeared` создана не позднее 2 мин; Given шаблон с частотой 2/мин; When частота стала 100/мин на 3 мин; Then создана аномалия `template_spike`.
- **Приоритет:** Should · **Зависит от:** FR-LAD-001, FR-MAD-001

#### FR-LAD-005 — Ограничение числа шаблонов
- **Требование:** Система должна ограничивать число шаблонов на сервис (по умолчанию 5000), вытесняя давно не встречавшиеся шаблоны (LRU) и учитывая вытеснения в метрике.
- **Обоснование:** Логи с неудачно замаскированными переменными иначе бесконечно растят дерево (администратор).
- **Приёмка:** Given 20 000 уникальных строк без общих шаблонов; When они обработаны; Then у сервиса ≤ 5000 шаблонов, а метрика вытеснений > 0.
- **Приоритет:** Must · **Зависит от:** FR-LAD-001

#### FR-LAD-006 — Стабильные идентификаторы шаблонов
- **Требование:** Система должна сохранять дерево шаблонов в чекпоинте (FR-STR-003) и обеспечивать неизменность идентификатора шаблона после перезапуска процессора и при перераспределении сервиса на другой экземпляр.
- **Обоснование:** Ссылки на шаблоны в инцидентах и алертах не должны «ломаться» после рестарта.
- **Приёмка:** Given шаблон с `template_id=T`; When процессор перезапущен и приходит строка того же шаблона; Then она получает `template_id=T`, а аномалия `new_template` не создаётся.
- **Приоритет:** Must · **Зависит от:** FR-STR-003, FR-LAD-001

### 4.7. Корреляция и RCA (RCA)

#### FR-RCA-001 — Формирование и закрытие инцидента
- **Требование:** Система должна объединять в один инцидент аномалии, начавшиеся в пределах 5 мин друг от друга на узлах, связанных в графе путём длиной не более 3 рёбер, добавлять в открытый инцидент новые подходящие аномалии и закрывать инцидент после 10 мин без новых и активных аномалий.
- **Обоснование:** Дежурный должен видеть один инцидент вместо 20 разрозненных аномалий.
- **Приёмка:** Given цепочка `frontend → checkout → payment`, и вносится задержка в `payment`; When аномалии возникли у всех трёх; Then существует ровно 1 инцидент, содержащий 3 аномалии; When сбой устранён; Then инцидент закрыт через 10–11 мин после исчезновения последней аномалии.
- **Приоритет:** Must · **Зависит от:** FR-MAD-001, FR-LAD-003, FR-TOP-001

#### FR-RCA-002 — Ранжирование кандидатов первопричины
- **Требование:** Система должна для каждого инцидента вычислять ранжированный список до 5 кандидатов первопричины (узлы графа и события изменений) с оценкой в диапазоне [0, 1], учитывая направление зависимостей (аномалия вызываемого объясняет аномалию вызывающего), время начала аномалий и силу аномалии, и пересчитывать его при изменении инцидента.
- **Обоснование:** Ядро ценности для дежурного (UC-01); метрика точности — NFR-ACC-002.
- **Приёмка:** Given 30 прогонов фиксированного набора внесённых сбоев (раздел 9, эксперимент E6); When инциденты сформированы; Then истинная причина входит в top-3 не менее чем в 80% прогонов.
- **Приоритет:** Must · **Зависит от:** FR-RCA-001

#### FR-RCA-003 — Доказательства кандидата
- **Требование:** Система должна для каждого кандидата первопричины предоставлять список доказательств: аномалии с их score и временем начала, связанные шаблоны логов с примерами, путь в графе от кандидата до затронутых узлов.
- **Обоснование:** Дежурный не доверяет «чёрному ящику»; доказательства позволяют подтвердить гипотезу за минуты.
- **Приёмка:** Given инцидент с кандидатом `payment-db-proxy`; When запрошен инцидент; Then у кандидата есть ≥ 1 аномалия-доказательство и путь до каждого затронутого узла инцидента.
- **Приоритет:** Must · **Зависит от:** FR-RCA-002

#### FR-RCA-004 — События изменений как кандидаты
- **Требование:** Система должна регистрировать события изменений Kubernetes (смена образа или spec у Deployment/StatefulSet/DaemonSet, масштабирование, изменение ConfigMap, на который ссылается workload) и включать событие в число кандидатов, если оно произошло у узла инцидента не ранее чем за 15 мин до начала первой аномалии.
- **Обоснование:** Значительная доля инцидентов вызвана изменениями; релиз — первый подозреваемый (UC-03).
- **Приёмка:** Given в 12:00 выкачен новый образ `recommendation`, а в 12:02 начались ошибки; When сформирован инцидент; Then событие деплоя `recommendation` присутствует в кандидатах с указанием версии образа «было → стало».
- **Приоритет:** Should · **Зависит от:** FR-RCA-002

### 4.8. Алертинг (ALR)

#### FR-ALR-001 — Правила алертов
- **Требование:** Система должна поддерживать правила трёх типов: (а) на инцидент с фильтром по затронутым namespace/сервисам; (б) на аномалию с минимальным score и фильтром по сигналу; (в) пороговое условие по RED-метрике (например, «доля ошибок ребра > 5%») — с параметрами severity, меток и каналов доставки.
- **Обоснование:** Разные команды хотят разные уровни шума; пороговые правила нужны для известных SLO (SRE, дежурный).
- **Приёмка:** Given правило `error_rate(frontend) > 0.05 for 2m`; When доля ошибок держится 6% 3 мин; Then создан алерт severity из правила.
- **Приоритет:** Must · **Зависит от:** FR-RCA-001, FR-MAD-001

#### FR-ALR-002 — Гистерезис срабатывания и разрешения
- **Требование:** Система должна переводить алерт в состояние `firing` только если условие выполняется непрерывно в течение `for` (по умолчанию 1 мин для пороговых правил и 0 для правил на аномалии и инциденты, у которых гистерезис уже обеспечен FR-MAD-001 и FR-RCA-001, — иначе нарушается NFR-ACC-001), а в `resolved` — если условие не выполняется непрерывно в течение `resolve_for` (по умолчанию 5 мин); для пороговых правил поддерживать раздельные пороги срабатывания и разрешения.
- **Обоснование:** Подавляет «дребезг» алертов на границе порога (дежурный).
- **Приёмка:** Given порог срабатывания 5% и разрешения 3%; When доля ошибок колеблется между 4% и 6% каждые 30 с в течение 20 мин; Then отправлено не более 1 уведомления о срабатывании и ни одного о разрешении.
- **Приоритет:** Must · **Зависит от:** FR-ALR-001

#### FR-ALR-003 — Дедупликация и группировка
- **Требование:** Система должна вычислять отпечаток (fingerprint) алерта по правилу и меткам и не отправлять повторное уведомление по алерту с тем же отпечатком, пока он в `firing` (кроме напоминания с интервалом по умолчанию 4 ч); алерты, относящиеся к одному инциденту, отправлять одним групповым уведомлением с ожиданием группы 30 с.
- **Обоснование:** Один инцидент — одно уведомление, а не 20 (дежурный).
- **Приёмка:** Given инцидент затрагивает 6 сервисов, и правила срабатывают по каждому; When прошло 30 с с первого срабатывания; Then отправлено 1 групповое уведомление с 6 алертами; повторных уведомлений в течение следующих 4 ч нет.
- **Приоритет:** Must · **Зависит от:** FR-ALR-001

#### FR-ALR-004 — Временное подавление (silence)
- **Требование:** Система должна поддерживать silence с матчерами по меткам (равенство, регулярное выражение), временем начала и конца, автором и комментарием; подавленные алерты не отправляются, но регистрируются и видны в UI с пометкой `silenced`.
- **Обоснование:** Плановые работы не должны будить дежурного (UC-06).
- **Приёмка:** Given silence `service=orders-db` на 2 ч; When в течение этого времени срабатывает алерт по `orders-db`; Then уведомление не отправлено, а алерт виден в списке со статусом `silenced` и ссылкой на silence.
- **Приоритет:** Must · **Зависит от:** FR-ALR-001

#### FR-ALR-005 — Каналы уведомлений
- **Требование:** Система должна доставлять уведомления в каналы: webhook (JSON с документированной схемой) — обязательно; e-mail (SMTP) и Telegram Bot API — опционально; уведомление содержит название, severity, затронутые сервисы, топ-3 кандидата первопричины и ссылку на инцидент в UI.
- **Обоснование:** Дежурный попадает из уведомления сразу к первопричине (UC-01).
- **Приёмка:** Given канал webhook на тестовый приёмник; When срабатывает алерт инцидента; Then приёмник получает JSON, валидный по опубликованной JSON Schema, содержащий ≥ 1 кандидата и абсолютный URL инцидента.
- **Приоритет:** Must (webhook), Could (e-mail, Telegram) · **Зависит от:** FR-ALR-003, FR-RCA-002

#### FR-ALR-006 — Гарантированная доставка с повторами
- **Требование:** Система должна повторять отправку при отказе канала с экспоненциальной задержкой от 1 с до 5 мин в течение не более 24 ч, передавать в каждом уведомлении ключ идемпотентности и сохранять очередь неотправленных уведомлений между перезапусками.
- **Обоснование:** Уведомление об инциденте не должно теряться из-за кратковременной недоступности канала (дежурный).
- **Приёмка:** Given приёмник webhook недоступен 10 мин, а компонент алертинга перезапущен в середине этого интервала; When приёмник восстановлен; Then все уведомления доставлены не позднее 5 мин после восстановления, у повторов один ключ идемпотентности.
- **Приоритет:** Must · **Зависит от:** FR-ALR-005

### 4.9. Хранение и срок хранения (STO)

#### FR-STO-001 — Срок хранения по типам данных
- **Требование:** Система должна автоматически удалять данные по истечении срока хранения, настраиваемого по типу данных и тенанту, со значениями по умолчанию: сырые события агента и спаны — 3 сут; логи — 7 сут; агрегаты 10 с — 7 сут; агрегаты 1 мин — 30 сут; агрегаты 1 ч — 180 сут; аномалии, инциденты, алерты — 180 сут.
- **Обоснование:** Предсказуемый объём диска (администратор).
- **Приёмка:** Given сырые события возрастом 4 сут; When прошёл цикл очистки (не реже 1 раза в час); Then они не возвращаются запросами, а агрегаты за тот же период доступны.
- **Приоритет:** Must · **Зависит от:** —

#### FR-STO-002 — Понижение разрешения (downsampling)
- **Требование:** Система должна строить из агрегатов 10 с агрегаты 1 мин и 1 ч, сохраняя возможность вычисления rate, доли ошибок и квантилей латентности с относительной ошибкой ≤ 2%.
- **Обоснование:** Исторические запросы и FR-TOP-006 за сроком хранения агрегатов 10 с.
- **Приёмка:** Given 1 ч данных; When сравниваются p95 по агрегату 1 ч и по сырым событиям; Then расхождение ≤ 2%.
- **Приоритет:** Should · **Зависит от:** FR-STR-001

#### FR-STO-003 — Защита от переполнения диска
- **Требование:** Система должна при заполнении тома хранилища на 85% удалять самые старые партиции сырых событий и логов досрочно (до 70%) и генерировать self-alert; при 95% — прекращать запись сырых событий, продолжая запись агрегатов, аномалий и инцидентов.
- **Обоснование:** Переполненный диск ClickHouse останавливает всю систему мониторинга именно тогда, когда она нужна (администратор).
- **Приёмка:** Given том 20 ГиБ заполняется со скоростью 1 ГиБ/мин; When достигнуто 85%; Then в течение 5 мин заполнение снижено до ≤ 70%, сработал self-alert, а агрегаты за последние 24 ч не удалены.
- **Приоритет:** Should · **Зависит от:** FR-STO-001, NFR-SELF-003

#### FR-STO-004 — Версионированные миграции схемы
- **Требование:** Система должна применять миграции схемы хранилища автоматически при старте, по порядку, однократно, с записью версии; миграции в пределах одной мажорной версии должны быть только расширяющими (добавление таблиц/колонок), без удаления и переименования.
- **Обоснование:** Обновление без потери данных и без ручных шагов (администратор).
- **Приёмка:** Given установка версии 1.0 с данными; When выполнен `helm upgrade` до 1.1 с новой миграцией; Then миграция применена ровно один раз (даже при 2 одновременно стартующих репликах), а данные 1.0 доступны.
- **Приоритет:** Must · **Зависит от:** —

### 4.10. API (API)

#### FR-API-001 — Единое описание и три протокола
- **Требование:** Система должна предоставлять API, описанное в одном наборе protobuf-схем, по протоколам gRPC, gRPC-Web и Connect (JSON и protobuf поверх HTTP/1.1 и HTTP/2) на одном порту.
- **Обоснование:** UI, CLI и сторонние интеграции используют один контракт (принятое решение, раздел 7.7).
- **Приёмка:** Given метод `GetGraph`; When он вызывается через `grpcurl`, через `curl` с `Content-Type: application/json` и из браузерного клиента; Then все три ответа семантически идентичны.
- **Приоритет:** Must · **Зависит от:** —

#### FR-API-002 — Запросы графа
- **Требование:** Система должна возвращать граф (узлы, рёбра, RED-метрики, статусы аномалий) для текущего момента или момента t с фильтрами по namespace, сервису, уровню агрегации, глубине окрестности узла и минимальному rate ребра.
- **Обоснование:** Основа UI и CLI (все персоны).
- **Приёмка:** Given граф из 200 узлов; When запрошена окрестность `checkout` глубиной 1; Then возвращены только `checkout`, его прямые соседи и рёбра между ними.
- **Приоритет:** Must · **Зависит от:** FR-TOP-001, FR-TOP-006

#### FR-API-003 — Поток изменений графа
- **Требование:** Система должна передавать подписчику серверным потоком изменения графа (добавление/удаление/обновление узлов и рёбер) с монотонным номером ревизии, полный снимок при подписке и не реже 1 раза в 60 с, и поддерживать возобновление подписки с ревизии, не старше 5 мин, без повторной передачи полного снимка.
- **Обоснование:** Живой граф в UI (UC-02) без опроса.
- **Приёмка:** Given подписчик на ревизии R; When соединение разорвано на 30 с и восстановлено с параметром `from_revision=R`; Then подписчик получает все изменения после R без пропусков ревизий и без полного снимка.
- **Приоритет:** Must · **Зависит от:** FR-API-001, FR-TOP-001

#### FR-API-004 — Запросы сигналов и инцидентов
- **Требование:** Система должна предоставлять запросы: RED-временных рядов узла/ребра за интервал; списка аномалий с фильтрами; списка инцидентов и инцидента с кандидатами и доказательствами; состояния детекторов.
- **Обоснование:** Страницы UI и команды CLI (дежурный, SRE).
- **Приёмка:** Given инцидент #N; When вызван `GetIncident(N)`; Then ответ содержит аномалии, кандидатов с оценками и доказательства по FR-RCA-003.
- **Приоритет:** Must · **Зависит от:** FR-RCA-003, FR-TOP-002

#### FR-API-005 — Управление правилами алертов и silence
- **Требование:** Система должна предоставлять операции создания, чтения, изменения и удаления правил алертов и silence с валидацией (синтаксис условия, корректность матчеров, конец silence позже начала) и возвращать ошибку `INVALID_ARGUMENT` с указанием поля.
- **Обоснование:** Управление алертингом из UI, CLI и GitOps-скриптов (SRE).
- **Приёмка:** Given запрос на создание silence с концом раньше начала; When он отправлен; Then возвращён `INVALID_ARGUMENT` с полем `ends_at`, и silence не создан.
- **Приоритет:** Must · **Зависит от:** FR-ALR-001, FR-ALR-004

#### FR-API-006 — Поиск логов
- **Требование:** Система должна искать записи логов за интервал не более 24 ч по сервису, уровню, идентификатору шаблона, trace_id и подстроке текста и возвращать частоты шаблонов за интервал.
- **Обоснование:** Подтверждение гипотезы первопричины по логам (UC-01).
- **Приёмка:** Given 1 млн записей логов за 1 ч; When запрошены записи шаблона T за 15 мин; Then возвращены все записи шаблона T этого интервала (сверка с прямым SQL-запросом) с пагинацией.
- **Приоритет:** Must · **Зависит от:** FR-LAD-001

#### FR-API-007 — Пагинация и ограничения запросов
- **Требование:** Система должна использовать курсорную пагинацию с размером страницы не более 1000 элементов для коллекций (логи, аномалии, инциденты, алерты), ограничивать время выполнения запроса 30 с (ошибка `DEADLINE_EXCEEDED`) и отменять запрос к хранилищу при отключении клиента. Исключение — чтение снимка графа (`GetGraph`): граф не пагинируется, потому что страницы разных ревизий несовместимы, а пагинацию нельзя добавить к RPC без ломающего изменения; его размер ограничивают лимиты графа и фильтры FR-API-002.
- **Обоснование:** Тяжёлый запрос одного пользователя не должен деградировать систему для всех (администратор).
- **Приёмка:** Given запрос с `page_size=5000`; When он выполнен; Then возвращено 1000 элементов и курсор; Given клиент разорвал соединение во время тяжёлого запроса; Then запрос в ClickHouse отменён в течение 2 с (`system.processes`).
- **Приоритет:** Must · **Зависит от:** FR-API-001

### 4.11. Веб-интерфейс (UI)

#### FR-UI-001 — Живой граф зависимостей
- **Требование:** Система должна отображать граф зависимостей с цветовой и формовой индикацией состояния узлов и рёбер (норма / аномалия / неактивно / данные неполны), обновляемый из потока FR-API-003 без перезагрузки страницы, и показывать баннер «данные устарели» с автоматическим переподключением, если обновлений нет дольше 15 с.
- **Обоснование:** Ядро темы №26 (UC-02).
- **Приёмка:** Given открытая страница графа; When у ребра появляется аномалия; Then его визуальное состояние меняется не позднее чем через 5 с после фиксации аномалии; When API недоступен 20 с; Then показан баннер, а после восстановления граф обновлён без действий пользователя.
- **Приоритет:** Must · **Зависит от:** FR-API-003

#### FR-UI-002 — Фильтрация, группировка и поиск
- **Требование:** Система должна позволять фильтровать граф по namespace, состоянию и минимальному rate, группировать узлы по namespace, переключать уровень агрегации и находить узел по имени с центрированием на нём.
- **Обоснование:** Граф из 200 узлов нечитаем без фильтрации (SRE).
- **Приёмка:** Given граф из 200 узлов в 10 namespaces; When выбран фильтр `namespace=payments` и состояние «аномалия»; Then отображаются только аномальные узлы `payments` и их рёбра.
- **Приоритет:** Must · **Зависит от:** FR-UI-001


#### FR-UI-003 — Панель узла и ребра
- **Требование:** Система должна по выбору узла или ребра показывать панель с графиками RED за выбранный интервал (с ожидаемым диапазоном детектора), списком активных аномалий, топ-10 шаблонов логов по частоте, источником данных (агент / OTLP) и состоянием детектора.
- **Обоснование:** Разработчик и SRE оценивают здоровье зависимости без перехода в другие инструменты.
- **Приёмка:** Given ребро с активной аномалией p95; When пользователь кликает по ребру; Then в течение 1 с открывается панель с графиком p95, где аномальный интервал выделен, а ожидаемый диапазон показан полосой.
- **Приоритет:** Must · **Зависит от:** FR-API-004, FR-API-006

#### FR-UI-004 — Режим «машины времени»
- **Требование:** Система должна позволять выбрать момент или интервал в прошлом, отображать граф на этот момент и проигрывать изменения интервала с шагом 10 с или 1 мин со скоростью от 1× до 60×.
- **Обоснование:** Разбор инцидентов постфактум (UC-04).
- **Приёмка:** Given интервал 03:00–03:30 вчерашнего дня; When запущено проигрывание со скоростью 30×; Then граф проходит интервал за 60 с ±5 с, и состояние рёбер на каждом шаге совпадает с FR-API-002 на соответствующий момент.
- **Приоритет:** Should · **Зависит от:** FR-TOP-006, FR-UI-001

#### FR-UI-005 — Страница инцидента
- **Требование:** Система должна для инцидента показывать: временную шкалу аномалий и событий изменений, подграф затронутых узлов с выделением кандидатов первопричины и их рангами, доказательства каждого кандидата с переходом к логам шаблона и к панели узла.
- **Обоснование:** Путь «уведомление → первопричина» (UC-01, NFR-USAB-002).
- **Приёмка:** Given инцидент с 3 кандидатами; When открыта ссылка из уведомления; Then без дополнительных кликов видны подграф, ранжированные кандидаты и доказательства кандидата №1.
- **Приоритет:** Must · **Зависит от:** FR-API-004

#### FR-UI-006 — Логи, сгруппированные по шаблонам
- **Требование:** Система должна показывать для сервиса и интервала список шаблонов с частотой, спарклайном частоты и пометками «новый» / «всплеск» / «исчез», а по выбору шаблона — записи этого шаблона с пагинацией.
- **Обоснование:** Ядро темы №29 в интерфейсе (разработчик, дежурный).
- **Приёмка:** Given у сервиса шаблон с аномалией `new_template`; When открыта вкладка логов сервиса; Then этот шаблон помечен «новый» и находится в первой пятёрке списка.
- **Приоритет:** Must · **Зависит от:** FR-API-006, FR-LAD-003

#### FR-UI-007 — Алерты и создание silence
- **Требование:** Система должна показывать список алертов с состояниями `firing` / `resolved` / `silenced` и позволять создать silence из карточки алерта с предзаполненными матчерами.
- **Обоснование:** Быстрое глушение шума дежурным (UC-06).
- **Приёмка:** Given алерт `firing` по `orders-db`; When пользователь с ролью `editor` нажимает «Silence» и подтверждает 2 ч; Then silence создан с матчером `service=orders-db`, а алерт переходит в `silenced`; пользователю с ролью `viewer` кнопка недоступна.
- **Приоритет:** Should · **Зависит от:** FR-API-005, FR-SEC-004

### 4.12. CLI (CLI)

#### FR-CLI-001 — Инциденты в терминале
- **Требование:** Система должна предоставлять CLI-команды `faultctl incidents list` (фильтры по статусу, интервалу) и `faultctl incidents get <id>` с выводом кандидатов первопричины и доказательств в форматах `table`, `json`, `yaml`.
- **Обоснование:** Дежурный и SRE работают из терминала и скриптов.
- **Приёмка:** Given 3 открытых инцидента; When выполнена `faultctl incidents list --status open -o json`; Then вывод — валидный JSON-массив из 3 элементов, а код возврата 0.
- **Приоритет:** Should · **Зависит от:** FR-API-004

#### FR-CLI-002 — Экспорт графа
- **Требование:** Система должна экспортировать граф (текущий или на момент t, с фильтрами FR-API-002) командой `faultctl graph export` в форматах DOT, JSON и Mermaid.
- **Обоснование:** Документация архитектуры и проверка MVP до появления UI (SRE, разработчик).
- **Приёмка:** Given граф Online Boutique; When выполнена `faultctl graph export -o dot | dot -Tsvg`; Then вывод без ошибок разбирается DOT-парсером `gonum/graph/encoding/dot` (BSD), и в нём 14 рёбер уровня workload.
- **Приоритет:** Must · **Зависит от:** FR-API-002

#### FR-CLI-003 — Диагностика установки
- **Требование:** Система должна предоставлять команду `faultctl doctor`, которая проверяет: совместимость ядра каждого узла (FR-AGT-010), готовность всех компонентов, связность агентов с приёмом, отставание обработки, заполненность диска, — и выводит по каждой проверке `OK` / `WARN` / `FAIL` с подсказкой.
- **Обоснование:** Администратор за 1 команду находит причину неработающей установки.
- **Приёмка:** Given один узел без BTF и остановленный процессор; When выполнена `faultctl doctor`; Then вывод содержит `FAIL` для этого узла и для процессора, а код возврата ненулевой.
- **Приоритет:** Should · **Зависит от:** FR-AGT-010, NFR-SELF-001

### 4.13. Развёртывание и эксплуатация (OPS)

#### FR-OPS-001 — Установка Helm-чартом с профилями
- **Требование:** Система должна устанавливаться одним Helm-чартом с профилями `dev` (по одной реплике каждого компонента, журнал без репликации) и `ha` (3 узла журнала с фактором репликации 3, 2 реплики ClickHouse + 3 узла ClickHouse Keeper, ≥ 2 реплики приёма, процессора и API, PodDisruptionBudget и anti-affinity для всех реплицированных компонентов).
- **Обоснование:** Разработка на ноутбуке и отказоустойчивая эксплуатация одним артефактом (администратор).
- **Приёмка:** Given чистый кластер kind 1.37; When выполнена `helm install faultline ./chart -f values-ha.yaml`; Then все поды `Ready` не позднее 5 мин, и `helm test` проходит.
- **Приоритет:** Must · **Зависит от:** —

#### FR-OPS-002 — Пробы здоровья
- **Требование:** Система должна предоставлять у каждого компонента liveness-пробу (процесс отвечает) и readiness-пробу (компонент может выполнять свою функцию: приём — запись в журнал доступна; процессор — владеет ключами и чекпоинт моложе 60 с; API — хранилище доступно).
- **Обоснование:** Kubernetes не должен направлять трафик в нерабочую реплику (администратор).
- **Приёмка:** Given журнал недоступен; When прошло 15 с; Then readiness приёма `false`, liveness `true`, и под не перезапускается.
- **Приоритет:** Must · **Зависит от:** —

#### FR-OPS-003 — Валидация конфигурации
- **Требование:** Система должна проверять значения Helm по JSON Schema до установки и конфигурацию каждого компонента при старте, завершаясь с сообщением, называющим неверный параметр и допустимые значения.
- **Обоснование:** Ошибка конфигурации обнаруживается при `helm install`, а не через час по пустому графу (администратор).
- **Приёмка:** Given `values.yaml` с `processor.window: "10"` (без единицы); When выполнена `helm install`; Then установка отклонена с сообщением о поле `processor.window` и ожидаемом формате длительности.
- **Приоритет:** Should · **Зависит от:** FR-OPS-001

#### FR-OPS-004 — Метрики самонаблюдения
- **Требование:** Система должна экспортировать с каждого компонента метрики в формате Prometheus (OpenMetrics) по перечню NFR-SELF-001 и логи в структурированном JSON-формате.
- **Обоснование:** Администратор наблюдает за системой наблюдения внешними стандартными средствами.
- **Приёмка:** Given установленный профиль `dev`; When Prometheus скрейпит все компоненты; Then все метрики из перечня NFR-SELF-001 присутствуют, а `promtool check metrics` не выдаёт ошибок.
- **Приоритет:** Must · **Зависит от:** —

### 4.14. Мультитенантность, RBAC и защита данных (SEC)

#### FR-SEC-001 — Аутентификация пользователей через OIDC
- **Требование:** Система должна аутентифицировать пользователей UI, CLI и API через внешний OIDC-провайдер (authorization code + PKCE для UI, device authorization grant для CLI) и сопоставлять группы из токена с ролями и тенантами.
- **Обоснование:** Единый вход и централизованное управление доступом (администратор).
- **Приёмка:** Given Dex с пользователем в группе `payments-oncall`, сопоставленной с ролью `editor` тенанта `team-payments`; When пользователь входит в UI; Then он получает доступ к данным `team-payments` с правами `editor`; запрос API без токена получает `UNAUTHENTICATED`.
- **Приоритет:** Should · **Зависит от:** FR-SEC-004

#### FR-SEC-002 — Токены приёма данных
- **Требование:** Система должна аутентифицировать агентов и OTLP-клиентов по токенам, привязанным к тенанту, хранить токены только в виде хэшей, поддерживать выпуск, отзыв и одновременное действие двух токенов для ротации; отозванный токен должен перестать приниматься не позднее 60 с.
- **Обоснование:** Защита от записи чужих данных и разделение данных тенантов на входе (администратор).
- **Приёмка:** Given действующий токен T; When администратор отзывает T; Then через 60 с запросы с T получают `UNAUTHENTICATED`, а запросы с новым токеном принимаются.
- **Приоритет:** Must · **Зависит от:** —

#### FR-SEC-003 — Изоляция данных тенантов
- **Требование:** Система должна определять тенант как набор namespaces кластера, привязывать каждое событие к тенанту на входе и ограничивать каждый запрос API данными тенантов вызывающего на уровне запроса к хранилищу; ребро между namespaces разных тенантов видно обоим тенантам, но узел чужого тенанта отображается обезличенно (`external-tenant`).
- **Обоснование:** Команды не должны видеть данные друг друга (UC-05).
- **Приёмка:** Given тенанты A и B и ребро A → B; When пользователь тенанта A запрашивает граф, инциденты и логи; Then он видит ребро до `external-tenant`, но ни одного имени сервиса, лога или метрики узла тенанта B (автоматический тест по всем методам API, NFR-SEC-006).
- **Приоритет:** Should · **Зависит от:** FR-SEC-002

#### FR-SEC-004 — Ролевая модель
- **Требование:** Система должна поддерживать роли в пределах тенанта: `viewer` (чтение), `editor` (+ управление правилами алертов и silence), `admin` (+ управление тенантами, токенами, сопоставлением групп), и отклонять действия сверх роли с кодом `PERMISSION_DENIED`.
- **Обоснование:** Минимальные привилегии (администратор).
- **Приёмка:** Given пользователь `viewer`; When он вызывает `CreateSilence`; Then получает `PERMISSION_DENIED`, и silence не создан.
- **Приоритет:** Should · **Зависит от:** —

#### FR-SEC-005 — Лимиты на тенант
- **Требование:** Система должна применять к каждому тенанту ограничение скорости приёма (по умолчанию 20 000 событий/с, алгоритм token bucket) и лимит кардинальности FR-STR-007 так, что превышение одним тенантом не снижает пропускную способность для остальных.
- **Обоснование:** «Шумный сосед» не должен выключить мониторинг остальным командам (администратор).
- **Приёмка:** Given тенант A шлёт 60 000 событий/с, тенант B — 5 000 событий/с; When нагрузка длится 5 мин; Then B получил 0 ответов 429, а A — 429 на превышение лимита.
- **Приоритет:** Should · **Зависит от:** FR-ING-005, FR-SEC-003

#### FR-SEC-006 — Маскирование PII в логах
- **Требование:** Система должна до записи в хранилище маскировать в телах и атрибутах логов: e-mail, номера телефонов в формате E.164, номера банковских карт (13–19 цифр с проверкой Луна), JWT, значения после `password=`, `token=`, `secret=`, `api_key=` — с поддержкой пользовательских правил и без возможности отключить встроенные правила для карт и JWT.
- **Обоснование:** Персональные данные и секреты в логах — юридический и репутационный риск (администратор).
- **Приёмка:** Given корпус из 10 000 строк логов с 500 заранее внедрёнными PII-значениями; When корпус принят; Then в хранилище 0 вхождений внедрённых значений (NFR-SEC-005).
- **Приоритет:** Must · **Зависит от:** FR-ING-001

## 5. Нефункциональные требования

### 5.0. Стенды и профили измерений

Все условия измерения в НФТ ссылаются на один из профилей. Профиль **L** обязателен и доступен с первого дня; профиль **S** — для проверки масштабирования и x86_64, используется при наличии доступа (открытый вопрос OQ-01).

| Профиль | Железо | Программная среда | Назначение |
|---|---|---|---|
| **L** (ноутбук) | MacBook Pro, Apple M1 Pro (8 производительных + 2 энергоэффективных ядра), 32 ГБ RAM, SSD | Linux-ВМ Docker Desktop arm64 (ядро 7.0 linuxkit, BTF и cgroup v2 подтверждены `make btf-check` 2026-11-05), 8 vCPU, 20 ГиБ RAM, 100 ГиБ диска; kind 1.37 с 1 control-plane и 3 рабочими узлами | Разработка, функциональные тесты, НФТ производительности на 1 экземпляр, хаос-эксперименты |
| **L1** (ноутбук, изолированный узел) | Как L | k3s, один узел в отдельной Linux-ВМ 4 vCPU / 8 ГиБ; бэкенд и генератор нагрузки — в другой ВМ | Замеры влияния агента на хост (NFR-AGT): на kind все узлы делят одно ядро, и kprobe каждого агента срабатывает на трафике всех узлов, что искажает замер |
| **S** (сервер) | 3 узла x86_64, по 8 vCPU / 32 ГиБ, NVMe, сеть ≥ 10 Гбит/с | Ubuntu 24.04 или Debian 12, kubeadm/k3s 1.37 | Масштабирование (NFR-PERF-007), x86_64-совместимость, повторение ключевых замеров |

Общие правила замеров: прогрев 5 мин перед измерением, длительность не менее 30 мин, если не указано иное; каждый замер повторяется 5 раз, в отчёт идёт медиана и разброс; генератор нагрузки работает на ресурсах, не пересекающихся с измеряемым компонентом (CPU-лимиты подов). «Событие» — один спан, одна запись лога, одна точка метрики или одна запись HTTP/gRPC-обмена агента.

Инструменты нагрузки (все с разрешительными лицензиями): `telemetrygen` (OTel Collector contrib, Apache 2.0) — OTLP; `vegeta` (MIT) — HTTP; `ghz` (Apache 2.0) — gRPC; Online Boutique (Apache 2.0) с его `loadgenerator` — сквозная нагрузка; Chaos Mesh (Apache 2.0) — внесение сбоев.

### 6.2. Минимальная версия ядра Linux

**Минимально поддерживаемая версия: 5.15 с `CONFIG_DEBUG_INFO_BTF=y` и cgroup v2.** Технический нижний предел — 5.8; 5.15 выбрана, чтобы ограничить матрицу тестирования LTS-ядрами, которые реально используются в дистрибутивах (Ubuntu 22.04 — 5.15, Debian 12 — 6.1, Amazon Linux 2023 — 6.1/6.12, Ubuntu 24.04 — 6.8).

| Возможность eBPF | Минимальное ядро | Зачем нужна |
|---|---|---|

| `BPF_MAP_TYPE_RINGBUF` | 5.8 | Передача событий в user space с сохранением порядка и без копирования на каждый CPU; учёт потерь при резервировании (FR-AGT-006) |
| `CAP_BPF`, `CAP_PERFMON` | 5.8 | Запуск агента без `CAP_SYS_ADMIN` и `privileged` (NFR-SEC-002) |

### 7.6. Алгоритмы детекции и RCA

**Детектор метрик**

| Критерий | EWMA + z-score (исходное) | Медиана/MAD + EWMA + сезонный профиль (**принято**) | Holt-Winters / STL | ML (Isolation Forest, LSTM-автоэнкодер) |
|---|---|---|---|---|
| Производительность | O(1) на точку | O(log n) на точку (скользящая медиана) | O(1)–O(n) | Тяжело для Go в потоке |
| Устойчивость к шуму | Аномалии «отравляют» среднее и дисперсию; суточный цикл даёт ложные срабатывания | Пробой оценки 50%; сезонность учтена | Хорошая, но нужна длинная история и подбор параметров | Нужны размеченные данные и переобучение |
| Холодный старт | Быстрый | 60 окон, сезонность — с 3/14 суток | Долгий (≥ 2 сезона) | Очень долгий |
| Лицензия, зрелость | Без зависимостей | Без зависимостей | gonum (BSD) | Почти нет Go-библиотек |
| Скоуп и сроки | Дни | 1–2 недели | +1–2 недели | Несоразмерно |
| Ценность для диплома | Хорошая база для сравнения | Сравнение «z-score против робастного против сезонного» — готовая экспериментальная глава (E4, E7) | Можно как третью точку сравнения (Could) | Высокая, но вне сроков |
| Риски | Шумные алерты (NFR-ACC-003 не выполнится) | Сезонность на сжатых сутках в эксперименте | Переусложнение | Срыв сроков |

**Рекомендация:** **принято** — робастный детектор как основной, EWMA + z-score остаётся базовой линией в экспериментах. **Уверенность:** высокая. **Затронутые требования:** FR-MAD-001, FR-MAD-002, FR-LAD-004, NFR-ACC-001, NFR-ACC-003.

**Детектор логов: Drain** — **оставить**. Drain — стандарт де-факто (лучшая или близкая к лучшей точность на LogHub при онлайн-работе и O(глубина дерева) на строку). Альтернативы: Spell и IPLoM уступают по точности, LLM-парсеры (LILAC и др.) не подходят для потока в 50k/с и требуют GPU. Существует Go-порт Drain3 (MIT) — использовать как эталон в E5, но писать свою реализацию из-за требований FR-LAD-005/006 (лимиты, стабильные ID, чекпоинт). **Уверенность:** высокая.

**RCA.** Исходное видение не фиксирует алгоритм. Рекомендация: реализовать две стратегии за одним интерфейсом и сравнить в E6: (1) базовая эвристика — самый глубокий по направлению вызовов аномальный узел с самой ранней аномалией; (2) персонализированный PageRank / случайное блуждание по аномальному подграфу с обратными рёбрами (семейство MicroRCA). Сравнение двух подходов на одних и тех же внесённых сбоях — научный результат главы. **Уверенность:** высокая. **Затронутые требования:** FR-RCA-002, NFR-ACC-002.

### 7.13. Противоречие в скоупе: gRPC без HPACK

gRPC работает только поверх HTTP/2, а метод (`:path`) и статус (`grpc-status` в трейлерах) передаются в HEADERS-кадрах, сжатых HPACK. HPACK хранит динамическую таблицу на всё время соединения, поэтому без её декодирования метод нельзя извлечь, а при подключении к уже установленному соединению — нельзя корректно извлечь даже с декодером. Варианты: (а) HPACK с состоянием в MVP + деградация до L4 для «старых» соединений; (б) uprobes на `grpc-go` — только для Go-сервисов; (в) gRPC только как L4. **Принято (а):** FR-AGT-002, FR-AGT-003. Перенос HPACK из «Развития» в MVP увеличивает объём работ января–февраля примерно на 2 недели — это учтено в плане (раздел 10) и в рисках.

## 12. Глоссарий

| Термин | Определение |
|---|---|
| eBPF | Механизм ядра Linux для запуска проверенных верификатором программ в ответ на события ядра (вызовы функций, системные вызовы, сетевые пакеты) без модулей ядра |
| BTF | BPF Type Format — описание типов ядра, позволяющее eBPF-программе работать с разными версиями ядра |
| CO-RE | Compile Once — Run Everywhere: компиляция eBPF-программы один раз с автоматической подстройкой смещений полей структур под ядро узла через BTF |
| kprobe / uprobe | Точки подключения eBPF к функциям ядра / функциям user space-процессов |
| Кольцевой буфер (ringbuf) | Общая для всех CPU очередь eBPF → user space; при заполнении новые события отбрасываются |
| HTTP/2-кадр, поток (stream) | Единица передачи HTTP/2; один поток — один запрос/ответ, мультиплексируемый в одном TCP-соединении |
| HPACK | Сжатие заголовков HTTP/2 (RFC 7541) со статической и динамической таблицами; динамическая таблица — состояние соединения |
| L4 / L7 | Уровни модели OSI: L4 — TCP-соединение (стороны, байты), L7 — прикладной протокол (метод, путь, статус) |
| OTLP | OpenTelemetry Protocol — стандартный протокол передачи трейсов, метрик и логов |
| OBI | OpenTelemetry eBPF Instrumentation — eBPF-агент проекта OpenTelemetry (бывш. Grafana Beyla) |
| Журнал (JetStream) | Персистентный реплицируемый лог сообщений NATS; R3 — фактор репликации 3 |
| Подтверждённое событие | Событие, на которое приём вернул отправителю успешный ответ (допущение A-08) |
| Событийное время / время обработки | Время возникновения события / время, когда система его обрабатывает |
| Окно (tumbling) | Неперекрывающийся интервал событийного времени фиксированной длины, по которому агрегируются события |
| Watermark | Оценка процессора «все события со временем меньше W уже получены»; закрывает окна |
| Allowed lateness | Насколько событие может опоздать относительно watermark и всё ещё быть учтённым |
| Ранний (предварительный) результат | Промежуточный результат окна до его закрытия; обеспечивает свежесть графа |
| Чекпоинт | Согласованный снимок состояния процессора и позиции чтения журнала для восстановления после сбоя |
| Идемпотентность | Свойство операции давать тот же результат при повторном выполнении |
| Кардинальность | Число уникальных комбинаций ключа (серий); взрыв кардинальности — неконтролируемый рост их числа |
| RED | Rate (запросов/с), Errors (доля ошибок), Duration (латентность) — базовые сигналы сервиса |
| Медиана / MAD | Median Absolute Deviation — медиана абсолютных отклонений от медианы; робастная мера разброса; коэффициент 1.4826 приводит её к σ для нормального распределения |
| EWMA | Экспоненциально взвешенное скользящее среднее |
| z-score | Отклонение значения от среднего в единицах стандартного отклонения |
| Сезонный профиль | Ожидаемое значение сигнала для каждого часа суток или недели |
| Холодный старт | Период, когда у детектора недостаточно истории для надёжной оценки |
| Drain | Онлайн-алгоритм извлечения шаблонов логов на основе дерева разбора фиксированной глубины |
| Шаблон лога | Текст лога с переменными частями, заменёнными плейсхолдерами (`user <NUM> logged from <IP>`) |
| Grouping Accuracy | Доля записей лога, сгруппированных в те же шаблоны, что и в эталонной разметке |
| LogHub | Открытый набор размеченных датасетов логов для оценки парсеров |
| Аномалия | Запись о статистически значимом отклонении сигнала от ожидаемого |
| Инцидент | Группа связанных во времени и в графе аномалий |
| RCA | Root Cause Analysis — определение первопричины инцидента |
| Кандидат первопричины | Узел графа или событие изменения, ранжированное как возможная причина инцидента |
| TTD | Time To Detect — время от возникновения сбоя до его обнаружения |
| Гистерезис | Разные условия срабатывания и сброса алерта, предотвращающие «дребезг» |
| Fingerprint | Хэш правила и меток алерта для дедупликации |
